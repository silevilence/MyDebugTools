# 标签自动发布

Status: ready-for-agent

## 发布者的操作

1. 发布前用 `generate-changelog` 准备版本号及仓库根目录的 `changelog.md`，把它们提交到准备发布的版本。
2. 推送指向该提交的标签，例如 `V0.0.1` 或 `v0.0.1`。首版识别前缀 V/v 加三段数字的正式版本。
3. 在对应标签的 GitHub Release 看到该版本的中文说明，下载 Windows x64 的 NSIS 安装包。

## 工作流

- GitHub Actions 从标签指向的提交构建。严格解析完整标签，排除普通分支、其他标签和预发布后缀。规范化后的数字版本用于核对宿主、安装包和更新清单；GitHub 链接保留实际标签大小写。
- 从 changelog 的二级版本标题取正文，保留列表、三级标题和换行，到下一个二级标题或文件末尾结束。只接受唯一且非空的匹配节。版本不一致、说明缺失、构建或上传失败时，日志指出出错项。
- Windows 构建环境提供 .NET 10、现有原生组件需要的 C++ 工具链及 NSIS。框架依赖的 x64 宿主配套内置插件、私有依赖及 x86/x64 后台组件。安装包文件名含产品、版本和宿主架构。
- 先准备 Release 草稿，资产齐备后公开。重跑可续传同一草稿；遇到已公开的同版本，核对后结束，内容冲突时明确报错。补发较旧版本时保留较新稳定版的更新入口。
- 首次安装和覆盖升级使用同一安装包。升级保留插件目录登记、用户设置、接口定义和 HTTP 请求日志。缺少运行时时提示所需架构，区分宿主启动和使用具体调试目标的要求。

## 验收

- 在同一台 Windows x64 测试环境安装两个本地版本，从安装入口启动宿主，核对版本、内置插件、x86/x64 样例和升级后的持久数据。
- 用大小写标签、相近版本（如 0.0.1 和 0.0.10）、说明缺失、空节及构建失败验证发布判断。用一次发布记录核对标签提交、Release 正文、资产名称和大小；重复运行不产生第二个公开版本。
- 发布后的资产优先核对平台摘要和 CI 记录。验收区分一次在线下载与后续本地复用。[自动更新规格](../0007-auto-update/spec.md)
